# Полный отчёт по переработке пользователей, ролей и прав доступа

Дата работ: 29 июля 2026 года  
Проект: `uzassets-platform-FULL`  
Область: RBAC v3, создание пользователей, вычисление эффективных прав, назначение ролей, UX/UI администрирования  
Состояние на момент составления: изменения находятся в рабочем дереве Git, коммит и развёртывание не выполнялись.

## 1. Итог работ

Система создания пользователей и назначения доступов переведена на согласованную модель:

- пользователь и его роли в компаниях создаются атомарно одним backend-запросом;
- одна компания может получить одну роль, а разные компании одного пользователя могут получить разные роли;
- глобальные роли, секторная область и роли в группах проходят проверку полномочий назначающего администратора;
- роль `admin` может назначать только владелец платформы (`OWNER`);
- эффективные права теперь одинаково учитываются в `/auth/me`, backend-проверках и frontend-интерфейсе;
- активные `deny` группы и пользователя имеют приоритет над обычными grant-источниками;
- истёкшие grant/deny больше не участвуют в расчёте прав;
- старый код `ai.chat` совместим с новым гейтом `ai.view`;
- каталог разрешений дополнен отсутствовавшими правами модулей;
- пошаговый мастер создания заменён единым рабочим экраном «учётная запись + доступ и роли»;
- выбор ролей унифицирован для создания, карточки пользователя и массовой операции;
- добавлены поиск, категории, описания ролей, итог назначения до сохранения, состояния ошибок и успешного результата;
- количество модулей в карточке пользователя теперь берётся из общего реестра, а не из устаревшего значения `16`.

## 2. Новая модель создания пользователя

### 2.1. Новый API-контракт

В `UserCreatePayload` добавлено поле:

```json
{
  "group_memberships": [
    {
      "group_id": "UUID группы компании",
      "role_code": "financier"
    }
  ]
}
```

Тип одной записи:

```python
class UserCreateGroupMembership(BaseModel):
    group_id: UUID
    role_code: str
```

Полный смысл полей создания:

| Поле | Назначение |
|---|---|
| `email` | Рабочий email и логин пользователя |
| `full_name` | ФИО |
| `department` | Подразделение |
| `job_title` | Должность |
| `organization_id` | Родная организация пользователя |
| `password` | Временный пароль |
| `must_change_password` | Обязательная смена пароля после первого входа |
| `role_codes` | Глобальные роли пользователя |
| `allowed_sectors` | Секторная область данных |
| `allowed_companies` | Старый совместимый формат области компаний |
| `group_memberships` | Новые назначения `группа/компания -> роль` |

### 2.2. Пример доступа к разным компаниям с разными ролями

```json
{
  "email": "user@example.com",
  "full_name": "Имя Фамилия",
  "password": "TemporaryPassword123!",
  "must_change_password": true,
  "role_codes": [],
  "group_memberships": [
    {
      "group_id": "11111111-1111-1111-1111-111111111111",
      "role_code": "viewer"
    },
    {
      "group_id": "22222222-2222-2222-2222-222222222222",
      "role_code": "financier"
    }
  ]
}
```

Результат: в первой компании пользователь будет наблюдателем, во второй - финансистом.

### 2.3. Атомарность

Новый порядок backend-операции:

1. Проверяется право администратора создавать пользователей.
2. Проверяются email, глобальные роли и предел полномочий назначающего пользователя.
3. Проверяется область организации и секторов.
4. Разрешаются и валидируются все `group_memberships`.
5. Создаётся объект пользователя.
6. Назначаются глобальные роли.
7. Добавляются записи `UserGroupRole` для всех групп и компаний.
8. Выполняется единый commit основной операции.
9. Добавляется аудит `rbac.user.create` с количеством групповых назначений.
10. Отправляется приглашение с временным паролем.
11. В ответ возвращаются memberships, эффективные права и статус отправки приглашения.

До этой переработки frontend сначала создавал пользователя, а затем отдельными запросами добавлял memberships. Ошибка посередине могла оставить пользователя созданным только частично. Теперь ошибка валидации группы или роли возникает до вставки пользователя, а назначения создаются в одной транзакции.

### 2.4. Валидация групповых назначений

Backend выполняет следующие проверки:

- все `group_id` существуют;
- все `role_code` существуют;
- одна группа не указана с двумя разными ролями;
- неизвестные группы возвращают `400`;
- неизвестные роли возвращают `400`;
- роль `admin` может назначить только `OWNER`;
- обычный администратор не может назначить роль с permissions выше собственных;
- группа или компания должна находиться в доступной актору области;
- назначение не может расширить компанию или сектор за пределы области актора.

### 2.5. Совместимость со старыми клиентами

Если старый клиент передаёт `allowed_companies`, но не передаёт `group_memberships`, backend пытается разрешить каждую ссылку как:

- UUID группы;
- UUID компании;
- код группы;
- код компании.

Если глобальная роль передана ровно одна, она используется как роль в группе. Иначе применяется минимальная роль `viewer`. Неизвестная ссылка приводит к `400`, а не к молчаливому пропуску доступа.

## 3. Эффективные права

### 3.1. Источники permissions

Расчёт теперь объединяет:

- permissions глобальных ролей пользователя;
- permissions роли пользователя внутри каждой группы;
- активные прямые group grants;
- активные прямые user grants.

Затем вычитаются:

- активные group denies;
- активные user denies.

Упрощённая формула:

```text
effective =
  (global role permissions
   + group role permissions
   + active group grants
   + active user grants)
  - active group denies
  - active user denies
```

`OWNER` и глобальная роль `admin` остаются backend super-admin bypass для проверок доступа.

### 3.2. Срок действия grant/deny

Для `GroupPermissionGrant` и `UserPermissionGrant` учитывается `expires_at`:

- `expires_at IS NULL` - запись действует без срока;
- `expires_at >= now(UTC)` - запись ещё активна;
- `expires_at < now(UTC)` - запись не участвует в расчёте.

Ранее repository-расчёт мог учитывать истёкшие записи.

### 3.3. Приоритет deny

Активный deny пользователя или любой группы исключает permission из итогового набора, даже если то же permission пришло из роли или другого grant-источника. Исключение составляет super-admin bypass на уровне backend-проверки.

### 3.4. Совместимость AI permissions

Исторически каталог использовал `ai.chat`, а новые маршруты и интерфейс используют `ai.view`.

Добавлена совместимость:

- backend-проверка `ai.view` принимает `ai.chat` как alias;
- итоговый repository-набор добавляет `ai.view`, если действует `ai.chat` и нет deny на `ai.view`;
- миграция выдаёт `ai.view` всем ролям, у которых был `ai.chat`;
- frontend распознаёт `ai.chat`, `ai.view`, `ai.manage` и `ai.admin`.

### 3.5. `/auth/me`

`AuthUserService.me()` стал асинхронным и получает permissions через `RbacV3Repository.effective_permission_codes(user.id)`.

Это означает, что клиент после входа получает тот же эффективный набор, который учитывает:

- глобальные роли;
- групповые роли;
- grants;
- denies;
- сроки действия;
- AI alias.

Если repository-вызов недоступен во время переходного состояния схемы, сохранён fallback на старый расчёт из загруженных ролей пользователя.

Маршруты `GET /auth/me` и обновление собственного профиля переведены на `await service.me(user, db)`.

## 4. Ограничение повышения привилегий

### 4.1. Глобальная роль admin

Создать пользователя с глобальной ролью `admin` может только `OWNER`.

### 4.2. Admin внутри группы

Роль `admin` внутри группы также может назначить только `OWNER`. Ограничение применяется в трёх сценариях:

- создание пользователя с `group_memberships`;
- одиночный upsert membership пользователя;
- массовая замена участников группы.

### 4.3. Privilege ceiling

Для администратора, который не является owner и не имеет super-admin bypass:

- загружаются его эффективные permissions;
- загружаются permissions назначаемой роли;
- назначение отклоняется, если роль содержит `admin`, `admin.*` или любое permission, отсутствующее у актора.

### 4.4. Scope ceiling

Администратор не может:

- указать пользователю организацию вне собственного доступа;
- выдать сектор, отсутствующий в его `allowed_sectors`;
- добавить membership в группу компании вне собственной области.

backend/alembic/versions/9b3_rbac_module_permissions.py

### 5.1. Добавляемые permissions

| Monitoring | `monitoring.view`, `monitoring.edit`, `monitoring.export`, `monitoring.manage` |
| AI | `ai.view`, `ai.manage` |

`investment.view` и `investment.edit` уже существовали, поэтому миграция добавляет только недостающие действия.

### 5.2. Автоматические назначения миграции

- роль `admin` получает все новые permissions;
- роли с `ai.chat` получают `ai.view`;
- роль `monitoring` получает `monitoring.view`.

Все вставки идемпотентны через `ON CONFLICT` или `NOT EXISTS`.

### 5.3. Runtime self-heal

В `runtime_migrations.py` добавлен `_patch_rbac_module_permissions(conn)` и его вызов из `ensure_yearly_rates_schema()`.

Runtime patch повторяет безопасную часть Alembic-миграции:

- создаёт или актуализирует недостающие permissions;
- выдаёт их роли `admin`;
- переносит `ai.chat -> ai.view` для ролей;
- выдаёт `monitoring.view` роли `monitoring`.

Alembic остаётся каноническим способом миграции. Runtime self-heal нужен для окружений, где приложение может запуститься до ручного обновления схемы.

### 5.4. Downgrade

Downgrade удаляет связи `role_permission` для введённых кодов, затем удаляет сами permissions. Пользовательские и групповые назначения, ссылающиеся на текстовые permission-коды, необходимо учитывать отдельно перед откатом production-базы.

## 6. Frontend-модель permissions

### 6.1. Канонические коды

Добавлена нормализация:

```text
invest -> investment
```

Frontend-реестр по-прежнему может использовать UI-код `invest`, но API сохраняет канонические permissions `investment.*`.

### 6.2. Специальные module mappings

Для модуля `admin` действия интерфейса сопоставляются с `admin.users`.

Для AI распознаются:

- view: `ai.view`, `ai.chat`;
- edit/export UI-возможности: `ai.view`;
- manage: `ai.manage`, `ai.admin`.

### 6.3. Преобразование уровней доступа

Уровни UI:

| Уровень | Генерируемые permissions |
|---|---|
| `none` | ничего |
| `read` | `{module}.view` |
| `write` | `{module}.view`, `{module}.edit`, `{module}.export` |
| `admin` | view, edit, export, manage |

Для alias-модулей используются канонические коды. Дубликаты удаляются.

### 6.4. Удалён лишний bypass роли CEO

Frontend раньше показывал полный доступ для ролей `admin` и `ceo`, тогда как backend super-admin bypass соответствует `admin`/owner. Bypass `ceo` удалён, чтобы UI не показывал действия, которые backend затем отклоняет с `403`.

### 6.5. Реестр модулей

Backend-сетка управляемых permissions включает 18 модулей:

```text
dashboard, bp, kpi, financials, credit, investment,
procurement, esg, governance, ratings, procurement_analysis,
consultants, tasks, pmo, reports, monitoring, ai, admin
```

В карточке пользователя итог теперь отображается как:

```text
Доступ к модулям · N из MODULE_REGISTRY.length
```

Устаревший hardcode `из 16` удалён.

## 7. Новый UX/UI создания пользователя

Основной компонент полностью переработан:

```text
frontend/src/components/rbac-v3/InviteUserModal.vue
```

### 7.1. Общая компоновка

Старый трёхшаговый мастер заменён одним широким экраном:

- слева - учётная запись;
- справа - область доступа и роли;
- снизу - постоянный итог и кнопка создания.

Администратор видит итоговую комбинацию профиля, области и ролей до отправки запроса.

### 7.2. Одиночное создание

Доступные поля:

- ФИО;
- рабочий email;
- подразделение;
- должность;
- организация;
- временный пароль;
- обязательная смена пароля при первом входе.

Для временного пароля доступны отдельные icon-кнопки:

- копировать;
- сгенерировать новый.

### 7.3. Массовое создание

Сохранён режим «Несколько»:

- строки разбираются как `email, ФИО`, `email; ФИО` или tab-separated;
- пустые и некорректные email отбрасываются;
- дубликаты email удаляются;
- при отсутствии ФИО используется часть email до `@`;
- каждому пользователю генерируется собственный пароль;
- общий scope и роли применяются ко всему списку;
- результат показывает успех или ошибку отдельно для каждой записи;
- успешные логины и пароли можно скопировать одним действием.

### 7.4. Три режима области доступа

#### Компании

- выводятся только группы, привязанные к компаниям;
- доступен поиск по названию и коду;
- выбранные компании поднимаются вверх списка;
- каждой выбранной компании назначается собственная роль;
- роль по умолчанию применяется при новом выборе компании;
- общую роль можно применить ко всем уже выбранным компаниям;
- payload отправляет отдельный `{group_id, role_code}` для каждой компании.

#### Секторы

- выбирается один или несколько секторов;
- выбирается одна или несколько глобальных ролей;
- отправляются `allowed_sectors` и `role_codes`.

#### Вся платформа

- ограничение компаний не задаётся;
- выбираются глобальные роли;
- интерфейс явно предупреждает, что доступ распространяется на данные всех компаний.

### 7.5. Валидация до создания

Кнопка создания активна только когда:

- в одиночном режиме заполнены ФИО и корректный email;
- в массовом режиме распознана хотя бы одна корректная строка;
- для company scope выбрана хотя бы одна компания;
- для sector scope выбран сектор и роль;
- для global scope выбрана роль;
- каталоги ролей и областей загружены.

В footer всегда отображается либо причина неготовности, либо итог назначения.

### 7.6. Предупреждение admin

Если среди глобальных или company-scoped ролей выбрана `admin`, интерфейс показывает предупреждение:

- роль даёт полный доступ;
- назначение разрешено только owner.

Окончательная проверка остаётся на backend.

### 7.7. Состояния результата

Для одного пользователя показываются:

- успешное создание;
- статус отправки email;
- логин;
- временный пароль;
- копирование данных входа.

Для массового режима показываются:

- количество успешных операций;
- отдельная строка на пользователя;
- пароль успешной записи;
- текст ошибки неуспешной записи;
- массовое копирование успешных credentials.

### 7.8. Защита от потери состояния

- при закрытии заполненной формы показывается подтверждение;
- overlay не закрывает окно во время сохранения;
- кнопка закрытия скрывается во время сохранения;
- Escape и событие close игнорируются обработчиком, пока выполняется запрос;
- повторная отправка блокируется флагом `saving`.

### 7.9. Адаптивность

- desktop: две колонки;
- средняя ширина: профиль и доступ переходят в вертикальный поток;
- mobile: scope-переключатели, секторы и поля переходят в одну колонку;
- company role select переносится под название компании;
- footer становится вертикальным;
- длинные названия обрезаются без нарушения сетки.

## 22. Группировка пользователей по компаниям

В реестр `/users` добавлено второе представление данных: `Список` и `Компании`. Режим `Компании` выбран по умолчанию, поскольку он показывает фактическую структуру назначений доступа, а единый список остаётся доступен для поиска конкретного человека и массовой работы без повторов.

### 22.1. Источник данных

Группировка строится не только по полю родной организации пользователя. В `UserBrief` добавлен компактный список `company_memberships`, сформированный из `UserGroupRole`, группы компании, роли и справочника компаний:

```json
{
  "company_memberships": [
    {
      "company_id": "UUID компании",
      "company_name": "Краткое или полное название",
      "group_id": "UUID группы компании",
      "group_name": "Название группы",
      "role_code": "financier",
      "role_name": "Финансист"
    }
  ]
}
```

Все назначения для загруженной страницы пользователей выбираются одним bulk-запросом. Дополнительный запрос на каждого пользователя не выполняется. В выдачу попадают только memberships групп, связанных с компаниями; свободные проектные и служебные группы не смешиваются с организационной группировкой.

### 22.2. Правила группировки

- пользователь отображается в каждой компании, где у него есть company membership;
- внутри компании показывается его роль именно для этой компании;
- глобальные роли пользователя сохраняются рядом и не теряются;
- если company memberships отсутствуют, используется родная компания `organization_id`;
- если отсутствует и membership, и родная компания, пользователь попадает в секцию `Без привязки к компании`;
- в режиме `Список` пользователь отображается один раз независимо от количества компаний;
- фильтры активности, безопасности, поиск и сортировка применяются до построения секций.

### 22.3. UX секций компаний

Теперь запись попадает в этот показатель только при одновременном отсутствии:

- глобальной роли в `user_role`;
- роли компании или группы в `UserGroupRole`.

Также `_hydrate_user` начал передавать фактическое поле `password_changed_at`, поэтому статусы возраста пароля в новом реестре основываются на серверных данных, а не остаются в состоянии `Нет данных`.

Поддерживаются `ru`, `uz-latn`, `uz-cyr` и `en`. При переходе нового пользователя по deep-link бот получает его `ui_locale` по токену и показывает карточку на языке платформы. Для обычного `/start` без токена язык берётся из настроек клиента Telegram, неизвестная локаль использует русский fallback. Узбекская кириллица формируется штатной транслитерацией системных строк. Имена, email, названия ролей и другие данные пользователя выводятся без перевода.

Обнаруженный deployment-разрыв также устранён: `ops/vm-autodeploy/deploy.sh` теперь не только разворачивает frontend и backend, но и пересобирает и пересоздаёт отдельный контейнер `uza-tg-bot`. Благодаря этому изменения `bot/i18n.py`, handlers, callbacks и formatter фактически попадают в production при каждом обновлении `master`.

## 33. Единый доступ ко всем AI-инструментам

Модуль `ai` в сетке доступа переименован из «AI-чат» в «ИИ: чат и аналитика». Уровень «Наблюдать» выдаёт каноническое разрешение `ai.view`, а «Нет доступа» создаёт эффективный запрет. Это разрешение теперь является единым пользовательским рубильником не только для страницы и карточки ИИ-ассистента, но и для встроенных AI-функций платформы.

Через `ai.view` включаются и отключаются:

- ИИ-ассистент в sidebar, мобильной навигации и маршрут `/ai-chat`;
- AI-анализ KPI;
- AI-анализ бизнес-плана;
- финансовый copilot, высокоуровневый AI-анализ и AI-прогноз показателей;
- AI-аналитик исполнения в Executive Dashboard;
- AI Executive Brief в Execution Summary;
- опция AI-резюме в PMO;
- ИИ-распознавание файлов в конструкторе проектов и задач.

На frontend добавлен единый `frontend/src/composables/useAiFeatureAccess.ts`. Он одновременно учитывает эффективное `ai.view`, прямой deny, роль/OWNER, режим доступа организации и глобальный выключатель владельца. Если доступ отозван, AI-кнопки, селекторы, панели и модальные окна исчезают реактивно; обычные расчётные и ручные функции соответствующих дашбордов продолжают работать.

Backend-защита расширена за пределы `/ai/*`. Маршруты `/monitoring/brief/{year}`, `/builder/ingest` и AI-вариант `/pmo/companies/{code}/status-reports` теперь вызывают тот же `require_ai_access`, проверяют scope API-ключа и глобальную активацию. Поэтому прямой HTTP-запрос не может обойти запрет, даже если скрытие интерфейса было обойдено вручную.

У Executive Dashboard удалён прежний внутренний owner-only барьер: пользователь с эффективным `ai.view` может запускать AI-аналитика в пределах доступных ему компаний. Сохранённые сводки больше не используют общий портфельный ключ; ключ версии `v2` включает пользователя, актуальную RBAC-область данных и выбранные фильтры. Это не позволяет получить сводку владельца или старую сводку после сужения доступа к компаниям.
